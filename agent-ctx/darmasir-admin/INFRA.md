# زیرساخت «درمسیر» — سند کامل INFRA

> این سند جواب دقیق درخواست «زیرساخت کامل بسازیم؛ از Worker کلادفلر خودم و
> یک دیتابیس رایگان کمک بگیریم» است. وضعیت فعلی، معماری هدف، آنچه همین حالا
> آماده استقرار است و گام‌های اجرایی — همه اینجا ثبت شده.

تاریخ: نوامبر ۲۰۲۵ — نگارش ۱

------------------------------------------------------------------------

## ۱. وضعیت فعلی (سندباکس توسعه)

| جزء | محل | وضعیت |
|---|---|---|
| اپ متروجو (APK Capacitor) | پروژه اصلی Next.js، پورت ۳۰۰۰ | دست‌نخورده (خط قرمز) |
| پنل مدیریت درمسیر | `mini-services/darmasir-admin/` — Next.js مستقل، پورت ۳۰۳۰، basePath `/panel` | فعال؛ از طریق مسیر `/panel` روی همان دامنه پیش‌نمایش |
| دیتابیس پنل (توسعه) | SQLite محلی: `mini-services/darmasir-admin/db/admin.db` | کار می‌کند ولی با پاک‌شدن سندباکس می‌میرد — **دلیل اصلی این سند** |
| API ابری آماده استقرار | `cloudflare/darmasir-api/` (Worker + D1) | کامل و آماده؛ فقط نیاز به `wrangler login` شما دارد |
| Workerهای صوتی قبلی | `cloudflare/` و `cloudflare-worker/` | دست‌نخورده — طبق سند توسعه، بدون دلیل حذف نمی‌شوند |

نکته مهم: سندباکس بین جلسات پاک می‌شود؛ در یک پاک‌سازی قبلی نسخه اول پنل و
کامیت‌های آن از بین رفت و از اسناد بازسازی شد. به همین دلیل «انتقال داده به
زیرساخت ابری» فقط مزیت هزینه نیست — شرط بقا داده‌هاست.

## ۲. معماری هدف (طبق سند توسعه — بخش ۸)

```
┌────────────────────┐        ┌─────────────────────────────┐
│ اپ اندروید (APK)    │─HTTPS─▶│ Cloudflare Worker:           │
│ Capacitor — استاتیک │        │  darmasir-api                │
└────────────────────┘        │  /api/v1/public/bootstrap    │
                              │  /api/v1/ads/:id/event       │
┌────────────────────┐        │        │                     │
│ پنل مدیریت (وب)     │─HTTPS─▶│        ▼                     │
│ Next.js (Pages یا   │        │  Cloudflare D1 (رایگان، 5GB) │
│ هر هاست Node)       │        │  + R2 برای رسانه (آینده)      │
└────────────────────┘        └─────────────────────────────┘
```

- **Workers** = محاسبات و منطق سمت سرور (همان پلتفرمی که Worker صوتی شما
  دارد؛ تجربه استقرار جدید لازم نیست)
- **D1** = دیتابیس SQLite مدیریت‌شده رایگان — ۵ گیگ فضای ذخیره‌سازی، بدون
  هزینه اضافی، در همان حساب و همان شبکه Worker
- **Pages (اختیاری مرحله بعد)** = میزبانی خودِ پنل؛ فعلاً پنل هرجا که Node
  هست اجرا می‌شود و فقط `NEXT_PUBLIC_API_BASE` را به Worker اشاره می‌دهد
- **KV (اختیاری)** = کش تنظیمات پرتکرار؛ فعلاً لازم نیست
- **R2 (اختیاری)** = تصاویر تبلیغات و رسانه‌ها؛ وقتی تبلیغ تصویری واقعی
  شد فعال می‌کنیم

چرا D1 و نه یک سایت دیگر؟ چون دیتابیس و Worker در **یک حساب، یک شبکه و یک
صورت‌حساب** قرار می‌گیرند، تأخیر صفر (بدون خروج از شبکه کلادفلر) دارند،
پلن رایگان آن برای این مقیاس کاملاً کافی است و هیچ کلید اتصال جداگانه‌ای
نیاز نیست (binding مستقیم). جایگزین‌ها پایین همین سند مقایسه شده‌اند.

## ۳. آنچه همین حالا ساخته و آماده است

`cloudflare/darmasir-api/` — Worker کامل با **همان قرارداد API پنل**
(پاسخ‌ها `{ok, data}` / `{ok:false, error}`، پیام‌های خطا فارسی):

| فایل | نقش |
|---|---|
| `worker.js` | کل API: ورود/خروج/حساب، آمار، خطوط، ایستگاه‌ها، کاربران، تبلیغات (+رویداد view/click)، تیکت‌ها و پیام‌ها، مدیران، تنظیمات، نسخه‌ها، گزارش رویدادها، `public/bootstrap` برای اپ |
| `schema.sql` | اسکیمای D1 — معادل ۱:۱ با `prisma/schema.prisma` پنل (۱۱ جدول + سطل نرخ) |
| `seed.sql` | داده واقعی: ۱۱ خط، ۱۹۹ ایستگاه، تنظیمات پیش‌فرض، نسخه فعلی |
| `gen-seed.ts` | بازتولید seed.sql از داده اپ (برای به‌روزرسانی آینده) |
| `wrangler.toml` | تنظیمات استقرار با binding دیتابیس |
| `README-FA.md` | راهنمای گام‌به‌گام استقرار |

امنیت همین حالا داخل Worker رعایت شده: PBKDF2-SHA256 برای رمزها، توکن
نشست ۳۲بایتی که فقط sha256 آن ذخیره می‌شود، نقش‌های SUPERADMIN/OPERATOR/
VIEWER، سقف ورود ۱۰ در ۵ دقیقه برای هر IP، audit log کامل، CORS
قابل‌تنظیم، بدون هیچ Secret در کد.

نقطه عمومی اپ: `GET /api/v1/public/bootstrap` (خطوط+ایستگاه‌ها+تنظیمات+
تبلیغ‌های فعال+آخرین نسخه، کش ۶۰ ثانیه) — APK برای استفاده از داده ابری
فقط به همین آدرس نیاز دارد؛ هیچ کلیدی داخل APK قرار نمی‌گیرد.

## ۴. گام‌های استقرار (خلاصه — کامل در README-FA.md)

پیش‌نیاز واحد: دسترسی به حساب کلادفلر شما (همان که Worker صوتی دارد).

```bash
# یک‌بار، روی سیستم شما:
cd cloudflare/darmasir-api
wrangler login
wrangler d1 create darmasir-db          # database_id را در wrangler.toml بگذارید
wrangler d1 execute darmasir-db --remote --file schema.sql
wrangler d1 execute darmasir-db --remote --file seed.sql
wrangler deploy
curl -X POST https://<worker-url>/api/v1/setup \
  -H "content-type: application/json" \
  -d '{"username":"admin","password":"<گذرواژه قوی>"}'

# اتصال پنل به ابر — در mini-services/darmasir-admin/.env.local:
NEXT_PUBLIC_API_BASE="https://darmasir-api.<subdomain>.workers.dev"
# و build دوباره پنل
```

بعد از این مرحله:
- داده‌ها روی D1 ماندگار می‌شوند و از پاک‌شدن سندباکس جان سالم می‌برند
- ورود پنل همان `admin` است (مدیر اولیه‌ای که با setup ساختید)
- `ALLOWED_ORIGINS` در wrangler.toml را از `"*"` به دامنه پنل محدود کنید

### پشتیبان‌گیری (طبق الزام امنیتی سند)

```bash
wrangler d1 export darmasir-db --remote --output backup-$(date +%F).sql
```

## ۵. گزینه‌های جایگزین دیتابیس رایگان (مقایسه تصمیم)

| سرویس | پلن رایگان | سازگاری | جمع‌بندی |
|---|---|---|---|
| **Cloudflare D1 (انتخاب)** | 5GB، ۵ میلیون خواندن/روز | binding مستقیم در Worker؛ worker.js همین الان نوشته شده | بهترین هم‌آهنگی با Worker موجود شما؛ صفر هزینه شبکه |
| Turso (libSQL) | 9GB، خواندن زیاد | آداپتور Prisma `@prisma/adapter-libsql`؛ از هر جایی قابل اتصال | اگر پنل را روی هاست Node جدا گرفتیم، انتخاب دوم |
| Neon (Postgres) | 0.5GB، خواب خودکار | Prisma بومی Postgres | سالم ولی برای این داده (متادیتا) بزرگ‌تر از نیاز |
| Supabase (Postgres) | 0.5GB | Prisma بومی + UI آماده | مزیتش داشبورد است؛ برای ما لازم نیست |

مهاجرت بین این‌ها آینده کاری سخت نیست چون کل قرارداد در لایه API است؛ فقط
worker.js/آداپتور عوض می‌شود و شِماها هم‌ارزند.

## ۶. ریسک‌ها و موارد باز

1. **اجرای استقرار به دست شماست** — طبق قاعده سند توسعه، هیچ اتصال خارجی
   را بدون اطلاعات واقعی «انجام‌شده» اعلام نمی‌کنیم؛ `wrangler login` نیاز
   به حساب شما دارد.
2. `database_id` دیتابیس D1 پس از ساخت باید در `wrangler.toml` گذاشته شود.
3. CORS فعلاً `"*"` است؛ **بعد از استقرار** حتماً به دامنه پنل محدود شود.
4. Worker روی پلن رایگان سقف ۱۰۰هزار درخواست/روز دارد — برای پنل و bootstrap
   اپ کاملاً کافی؛ اگر رویدادهای تبلیغ منفجر شد، آن‌ها را به KV بافر
   می‌کنیم (تغییر کوچک، جایش همین‌جا ثبت شد).
5. انتقال نشست‌های فعلی SQLite محلی به D1 لازم نیست (داده‌های واقعی = خطوط
   و ایستگاه‌ها که در seed.sql همان‌ها هستند).
